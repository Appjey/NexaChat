# Клиенты NexaChat: сохранять мультиплатформенность

Предложение на согласование · 31 октября 2026

**Рекомендация: сохранить общую React-базу, улучшить платформенные оболочки и добавлять нативные интеграции там, где они решают конкретную проблему. Полную разработку отдельных UI под каждую ОС сейчас не начинать.** Редизайн можно выпустить независимо от этого решения.

## Что проверено

Срез: `main`, commit `36a9d5e95ebe818d8dc31ab108c6b2cbf3098c2a`, репозиторий Appjey/NexaChat. Проверены README, package.json, Electron-конфигурация, исходники ChatsPage, ChatWindow, стили и список платформенных файлов.

- Web: React 19, TypeScript, Vite, Bootstrap; общая логика чатов, ключей, вложений и WebRTC.
- Android: Capacitor 8, FCM, share, файловые операции, биометрия и обновления APK.
- Desktop: Electron 39; в конфигурации сборки указан macOS arm64. Это общий web UI в desktop-оболочке, а не доказательство выпуска для Windows и Linux.
- В текущем checkout нет каталога `macos` со SwiftUI-клиентом, iOS-проекта или настроенной поставки Windows/Linux. Единственная зарегистрированная исходная рабочая область Orca — main; для дизайна создана отдельная.
- Есть E2E, группы, вложения, ответы, черновики, read receipts, закрепы и звонки. Отдельный клиент должен воспроизвести эти сценарии, а не только внешний вид чата.

Замеров потребления памяти, времени старта, батареи, качества звонков и распределения пользователей по ОС нет. Вывод ниже — архитектурная оценка, а не результат сравнения производительности.

## Сравнение вариантов

| Подход | Что получаем | Что придётся поддерживать | Вывод |
|---|---|---|---|
| React + Capacitor + Electron | Общие UI, E2E и поведение; единый редизайн | Качество WebView, жизненный цикл, системные мосты, desktop-ресурсы | Основной путь сейчас |
| Общая база + нативные модули | Системные звонки, push, share, secure storage без дублирования всего интерфейса | Swift/Kotlin-модули и тесты жизненного цикла | Предпочтительное развитие |
| SwiftUI, Kotlin/Compose и отдельные desktop UI | Максимальная свобода системного UX и оптимизации | Несколько UI, история/синхронизация, E2E, доступность, тесты и релизы для каждого | Только после подтверждённой потребности |
| Замена Electron другой оболочкой | Потенциально иная стоимость runtime | Новые мосты, WebRTC, обновления, signing, регрессии WebView | Отдельный эксперимент после профилирования |

Мультиплатформенность продукта и общая кодовая база — разные свойства. Нативные приложения тоже могут покрывать несколько ОС, но цена синхронизации функций вырастет. Общее API само по себе не устраняет дублирование клиентской логики.

## Рекомендация по платформам

**Web.** Сохранить как самостоятельный клиент и эталон протокола. Общие токены и дизайн-компоненты, адаптивный layout, клавиатура и доступность.

**Android.** Сохранить Capacitor. Сначала проверить FCM, восстановление после выгрузки процесса, входящий звонок на заблокированном экране, обработку разрешений, share и клавиатуру. Проблемы этих интеграций не означают, что нужно переписывать весь UI. Нативный Kotlin-клиент рассматривать, если оптимизации и мосты не дают приемлемого результата на целевых устройствах.

**macOS.** Сначала профилировать Electron и довести меню, shortcut, badge, уведомления, системные диалоги и доступность. SwiftUI оправдан, если macOS — основной рынок и системный UX является самостоятельной ценностью. Если существует отдельная native-ветка, сначала сверить её с текущим API и функциональным набором; её наличие не подтверждено этим checkout.

**Windows/Linux.** Не начинать отдельные UI без аудитории и требований. При необходимости сначала подтвердить сборку и тестирование общей desktop-оболочки. Нынешняя конфигурация macOS не гарантирует готовую поставку на этих ОС.

**iOS.** Это новая платформа для данного checkout. Начать с проверки жизненного цикла звонков, APNs, PushKit/CallKit и secure storage в тонком прототипе с Capacitor. Apple требует CallKit при обработке VoIP PushKit для приложений, собранных с iOS 13 SDK и новее. Это требует нативной интеграции звонка, но само по себе не требует полного SwiftUI-интерфейса. UI и API для iOS не включать автоматически в первый релиз редизайна.

## Как принять решение на данных

Сначала согласовать минимальные устройства и набор ОС. На одной сборке и одном наборе данных измерить: cold start до интерактивного списка, idle RAM/CPU, плавность истории, восстановление WS, повторную доставку без дублей, уведомления и звонки в foreground/background/locked/terminated состояниях. Энергопотребление измерять на физических мобильных устройствах. Не записывать содержимое сообщений, имена файлов, ключи или адресную книгу в телеметрию.

Предлагаемые стартовые бюджеты, **не текущие результаты**:

- Cold start p95 до интерактивного списка: ≤ 2 с desktop и ≤ 3 с Android на согласованном устройстве и локальном наборе данных; сетевую загрузку учитывать отдельно.
- Idle CPU медиана ≤ 1% за 5 минут без звонков и синхронизации; RAM сначала зафиксировать baseline, затем согласовать бюджет на целевой машине.
- Прокрутка истории: не менее 95% кадров в бюджете частоты экрана на целевом устройстве, с отдельно измеренной загрузкой/дешифровкой.
- Звонки/push: матрица ОС × жизненный цикл × сеть; фиксировать задержку и пропуски. Не обещать 100% доставки push без учёта сети и ограничений ОС.
- Контрактные crypto-fixtures: web ↔ каждый клиент, включая группы и вложения; ни одной тихой потери/дублирования сообщения в контролируемых reconnect-тестах.

Если ключевой сценарий остаётся за бюджетом после профилирования и двух ограниченных циклов исправлений, сделать native spike только на проблемной ОС. Сравнить одинаковый сценарий и функциональный набор. Решение о полном клиенте принимать при наличии измеримого выигрыша, владельца платформы, плана паритета функций и независимого бюджета сопровождения.

## План

1. Выпустить дизайн-систему и обновлённый React UI на существующих клиентах.
2. Снять baseline; улучшить системные интеграции Android/macOS.
3. При реальном запросе на iOS — отдельный прототип звонков/push, затем оценка поставки.
4. Вернуться к отдельному UI только после измерений. Не совмещать переписывание криптографии, смену протокола и ребрендинг в одном релизе.
